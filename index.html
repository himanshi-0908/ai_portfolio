Failure analysis

Engineering

  • One schema, four pipelines. Every retriever returns the same PipelineResult, so adding a fifth means implementing one interface.
  • Rank fusion over score fusion. Dense and BM25 scores aren’t comparable and weight tuning never transfers. RRF fuses on rank: Σ 1/(k + rank).
  • Metrics are unit-tested against hand-computed fixtures — a benchmark with wrong scoring is worse than none.

AI / ML

  • Retrieval: Recall@K for coverage, Precision@K for noise, MRR for the first hit, nDCG@K for ordering.
  • Generation: LLM-judged context relevance, faithfulness and answer relevance.
  • Stated limitation. The eval set comes from the same model family that answers, so numbers are relative, not absolute.

Results

Top-5, 8 queries. Two pipelines measured; two excluded the harness is at fault, not the strategy.

Pipeline Recall@5 Precision@5 MRR Retrieval
Naive dense 1.000 0.400 0.917 2,107 ms
Query rewriting 1.000 0.375 0.733 2,072 ms
Hybrid + RRF zero chunks returned — under investigation 4,187 ms
Hybrid + reranker same fault 4,128 ms

Ranking was the constraint, not coverage. Rewriting held recall at 1.000 but dropped MRR from 0.917 to 0.733 same chunks, ranked lower.

Excluded: hybrid scored zero at double the latency — a defect, not a result. nDCG too: it exceeds 1.0, which is impossible.

Challenges

Trusting my own benchmark. A wrong nDCG produces confident wrong conclusions — which is exactly how the normalization bug above got caught.

Architecture & evaluation

How I know it works.

Retrieval always returns something and a model always answers — both independent of whether either was right. The engineering is in the measurement.

Metrics I measure, and what each one catches

Metric Question it answers What it catches that the others miss
Recall@K How much of the relevant material made it into the top K? Ranks well, drops what matters.
Precision@K How much of what came back was actually relevant? Context padded with noise.
MRR How highly did the first relevant chunk rank? Retrievable but buried below the cutoff.
nDCG@K Is the ordering itself good, not just the membership? Same recall, different usefulness.
Faithfulness Is the answer grounded in the retrieved context? Confident hallucination on correct retrieval.
Context relevance Was the retrieved context on-topic at all? Retrieval failure vs generation failure.
Latency What did the quality cost? Accuracy bought at unusable speed.

Implemented and unit-tested in Ragvexa. Knovia’s threshold was derived the same way measured, not guessed.

What this demonstrates

Engineering

  • Typed artefacts per stage, so failures are attributable to a stage rather than to “the pipeline”.
  • Evaluation as a gate, not a report. A newly trained model is compared against the deployed one and only promoted to the registry if it clears the threshold.
  • Model versioning in S3, so a deployment can be rolled back to a specific artefact instead of retrained and hoped for.
  • Logging and exception handling throughout — silent failure in a scheduled run is worse than loud failure.
  • CI/CD via a self-hosted runner build, push to ECR, deploy to EC2 on merge. Ran end to end against a live instance, since decommissioned rather than left accruing cost.
